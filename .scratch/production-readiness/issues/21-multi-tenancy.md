# 多租户边界拷问

Type: grilling
Status: resolved

## Question

> **07/11 已决(2026-08-11)**:单用户/单租户配额(速率与累计)归本票与 11 成本治理;11 已定会话/绑定级两档预算 + 归因三级标签,**租户维度配额与按周期滚动配额(日/月)归本票同炉**(11 已留归因扩展位)。

框架为**多租户**提供到什么深度?(参考文档一.1 多租户实例隔离、七.3 按租户权限、十.3 按部门配额。第二轮 Q2 已决:以边界拷问票入图,不预设做或不做)

需回答:
1. **做不做**——租户隔离(数据/配置/配额)哪些归框架;租户系统本身(租户注册/认证/管理)明确不做
2. **机制边界**——若做:tenantId 是否贯穿核心模型(sessionId 之外的第一等维度?),还是只作存储与配置的透明维度
3. **接缝**——五 SPI 的租户维度(表结构/键设计);四层配置的租户级覆盖;与 11 成本治理(按租户配额)、14 工具权限(按租户可见性)的协同

答题要求:同 08 号票(做/不做 + 机制边界 + 接缝;借鉴成熟实现并注明来源)。

## Answer

(2026-08-11,grilling 收口,三问全采纳推荐)

**决策:部分做**——tenantId **透明维度**贯穿 + 命名空间级逻辑隔离;租户系统与强隔离不做。

**机制边界(管什么/不管什么)**:
- **tenantId 透明维度**:在存储键命名空间(Redis 前缀/JDBC 表列)、配置、配额、归因四层透明贯穿;**核心模型(session/轮次/消息)不动**,不立 sessionId 之外的第一等维度
- **来源 = 绑定级/spawn 声明**(同 14 主体上下文哲学:调用方声明、框架不认证,一旦传入全链贯穿)
- **隔离强度定级 = 命名空间级逻辑隔离**:业界共识(LangSmith 官方明示多租户为应用层逻辑隔离);参照系(toB 私有化+企业内部助手)以单部署单租户或部门级弱多租户为主,逻辑隔离够用 `> 【推演】`(参照系定级);**强隔离(行级安全/按租户加密密钥/跨租户访问检测)不做**——无一框架内建
- **不新增第五层配置**:租户级 = 绑定级按租户实例化
- **租户配额(与 11 同管线)**:租户维度配额 = 11 预算管线的租户实例化(归因扩展位已留);**周期滚动配额(日/月重置窗口)落本票同炉**——11 累计制硬顶之外的窗口形态
- **不管**:租户系统本身(注册/认证/管理)、按租户计费出账(归业务)

**接缝**:
- 五 SPI:租户维度 = 键前缀/表列,SPI 契约扩展 + **契约测试补租户隔离用例**(同 store 契约测试模式);键设计细则留 Spec
- 11:租户配额复用预算管线(告警→降级链→阻断三级动作同享);07:租户维度速率配额同理实例化
- 14:租户 = 主体属性之一,权限矩阵可按租户维度授权
- 22:按租户删除/留存(部门级数据清理)依赖本维度;18:fork 不跨租户(元数据校验)

- CrewAI memory scope(记忆按作用域命名空间隔离——命名空间级隔离形态)— https://github.com/crewAIInc/crewAI

# RAG 检索治理(边界拷问)

Type: grilling
Status: resolved

## Question

**RAG 检索中间层管控**是不是 Harness 层的事?(参考文档六:检索参数运行时调整/top-k 阈值管控/结果过滤去重/文档权限过滤/检索失败兜底/知识库版本绑定)

需回答:
1. **做不做**——RAG 治理是框架职责,还是用户业务层/Spring AI 层的事;这是边界拷问,"不做"是完全合法的答案(检索本质上是工具调用的一种?)
2. **机制边界**——若做:管什么(参数管控/权限过滤/兜底),不管什么(检索质量、embedding 选型);若不做:哪些诉求能被既有机制吸收(检索作为 MCP 工具→工具治理家族已覆盖?)
3. **接缝**——若做:与工具治理(09/14)的关系;与 14 工具权限(文档权限过滤)的协同

答题要求:同 08 号票(做/不做 + 机制边界 + 接缝;借鉴成熟实现并注明来源)。

## Answer

(2026-08-11,grilling 收口,两问全采纳推荐——首轮 Q2 误点"补做文档 ACL",用户明示更正为推荐项后重确)

**决策:不做专门 RAG 治理机制**——**检索即工具**,RAG 治理划界给检索层(向量库/搜索层);业界共识(主流框架均无内建,框架只做接口)。

**机制边界(管什么/不管什么)**:
- 参考文档六的诉求逐条被既有机制吸收,无遗漏:
  - 检索参数运行时调整 / top-k 阈值管控 → **09 按工具策略**(工具级配置)
  - 结果过滤去重 → **09 清洗**;检索失败兜底 → **09 重试/清洗/兜底 + 工具熔断**
  - 文档权限过滤 → **检索层内部语义**(哪些文档对谁能见是索引结构与查询语义的事);框架做且仅做 **14 主体上下文全链贯穿**(检索工具入参/ToolContext 携带主体,检索层凭此过滤)——**框架供"谁",检索层判"能见什么"**
  - 知识库版本绑定 → **23 已决**:工具集版本化 = 服务器侧职责
  - 检索质量 → **19 评估闭环**(LangSmith RAG 评估器蓝本:检索质量纳入评估,工具轨迹可读)
- 检索结果作证据进证据链(工具返回即证据,evidence-id 已有)
- **唯一增量**:langgraph-bigtool 模式(工具集超规模时语义检索选择注入,而非全量挂 schema)作 **ToolSetProvider 增强候选留 Spec**,本票不承诺
- **不管**:embedding 选型、索引生命周期、新鲜度、引用强制、检索质量优化(全归检索层)

**接缝**:
- 检索以 MCP 工具 / ToolCallback 接入 → 09 容错/熔断/缓存、14 权限、07 扇出**全部自动生效**,零增量
- 14:主体上下文贯穿是文档 ACL 的唯一框架侧接缝
- 19:检索质量评估走评估闭环(LLM-judge + 工具轨迹)

**借鉴**:
- 业界共识确认:检索的新鲜度/ACL 过滤/引用强制/索引生命周期,主流 Agent 框架均无内建——RAG 治理由向量库/搜索层承担,框架只做接口(01 票维度 15)
- LangChain 标准 retriever 接口(框架只做接口的形态先例)
- langgraph-bigtool(大规模工具集的语义检索选择——工具供给侧候选,留 Spec)— https://github.com/langchain-ai/langgraph-bigtool
- LangSmith RAG 评估器(检索质量纳入评估闭环)— https://docs.langchain.com/langsmith/evaluation-concepts

# 工具权限模型(RBAC/黑白名单/工具开关)

Type: grilling
Status: resolved

## Question

HITL 门禁(危险工具人工授权)之外,是否需要**结构性工具权限**?(参考文档五.1 工具开关/黑白名单、五.2 按会话/用户隔离可调用工具列表、七.3 RBAC)

需回答:
1. **做不做**——按主体(用户/角色/scope)的工具可见性与可调用性控制是否框架职责;RBAC 做到哪(提供判定钩子 vs 完整权限系统);主体从哪来(框架不管认证,只接收主体上下文?)
2. **机制边界**——结构性权限(事先定死谁能用什么)与 HITL(运行时个案授权)的层次关系:结构权限先行过滤、HITL 兜底?
3. **接缝**——与 ToolSetProvider SPI(工具集供给)的关系——权限是供给时的过滤还是调用时的拦截;与 MCP 热插拔(动态工具集)的协同;与 HITL 门禁 state 标记的关系;权限判定事件进 observability/审计(16)

答题要求:同 08 号票(做/不做 + 机制边界 + 接缝;借鉴成熟实现并注明来源)。

## Answer

(2026-08-11,grilling 收口,三问全采纳推荐)

**决策:做**——工具权限判定平面;业界空白,Spec 标 `> 【推演】`。

**机制边界(管什么/不管什么)**:
- **权限判定平面**:主体上下文 × 静态授权矩阵(角色 × 工具组 allow/deny,配置驱动);默认实现内置,SPI 可接外部授权系统(OPA 等);工具开关/黑白名单(参考文档五.1)作为矩阵退化形态(全局 allow/deny)由同一平面承载
- **两层模型**:L1 **结构权限**(配置时静态授权,答"能不能")与 L2 **HITL**(运行时个案授权,答"这次行不行")正交叠加;L1 不过滤掉的工具才可能进 HITL 视野
- **双执行点**:供给时过滤(ToolSetProvider 按主体上下文过滤,模型看不见无权工具——消除注入诱导靶子)+ 调用时拦截(beforeTool 再查,防 MCP 热插拔中途上架绕过——防御纵深)
- **主体上下文调用方声明**:spawn/绑定级传入主体标识(用户 ID/角色集);框架**不认证**(认证归应用层 Spring Security 等),只保证主体一旦传入,判定/过滤/审计全链贯穿
- **不管**:认证、用户/角色管理体系(租户系统归 21);细粒度到参数级的权限(留 Spec 评估)

**接缝**:
- 判定平面挂 ToolSetProvider(供给)+ beforeTool(拦截);判定事件进 observability 并喂 16 审计证据链(谁的主体下被允许/拒绝)
- 策略走 policy 四层配置;与 MCP 热插拔协同(刷新后新工具默认按矩阵重新判定)

**借鉴**:
- OpenAI Agents SDK needs_approval + 工具过滤(审批+过滤体系化先例)— https://openai.github.io/openai-agents-python/human_in_the_loop/
- 业界空白确认:RBAC 矩阵无一框架内建(01 票维度 4)——矩阵形态取 RBAC 最简形(主体×工具×allow/deny),`> 【推演】` 标注

# 悬空调用修复规则

Type: grilling
Status: resolved
Blocked by: 06

## Question

悬空调用（dangling tool call）的检测与修复细则：什么算悬空（assistant 消息含 tool_calls 但后续无对应 tool 结果）？加载历史时的修复策略——直接剔除整条违规消息，还是补一条合成结果消息（各模型 API 对孤儿 tool_calls 的容忍度不同）？修复动作是否记录到可观测层？跨实例接管时如何区分"悬空"与"另一实例正在执行中"（租约/心跳）？

## Answer

**定案：租约即判据 + 视图层现做（完全悬空剔除 / 部分悬空合成）+ 先重试后修复 + Event 审计。**

1. **判据 = 租约**：加载方持有会话租约（ticket 04/06）即权威——前任持有者遗留的一切未完成 tool_call 一律按悬空处理，不引入心跳/时间阈值等新机制。
2. **入口顺序：先重试，后修复**。续接加载发现未完成 tool_call 时，先走工具重试/重放流程；**重试全部失败后才进入悬空修复**。重试策略（次数、幂等边界、与 HITL 的交互）另立 ticket 29 细化。
3. **检测**：加载历史构建注入视图时，扫描 assistant 消息的 tool_calls，凡无对应 tool 结果消息者即为悬空。
4. **修复 = 视图层现做**：不破坏消息只追加原则（ticket 06），与微压缩同一注入前管道，无写路径：
   - **完全悬空**（该消息所有 tool_calls 均无结果）：整条从注入视图剔除；若消息含正文文本，正文降级为普通 assistant 消息保留，仅剔除 tool_calls 部分。
   - **部分悬空**：已完成的 tool_call 与其结果保留；缺失的补一条合成结果「执行被中断，结果未知」，带元数据标记以区别真实工具返回。
5. **审计 = 记 Event**：每次修复发一条 Event（被修复消息 id、悬空 tool_call 名列表、判据=租约、剔除/合成方式），挂会话 Span 下；库内原文不动，现场可随时回查。与 ticket 13（Span+Event 模型）衔接。

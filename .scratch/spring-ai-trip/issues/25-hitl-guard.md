# HITL 危险操作守卫设计

Type: grilling
Status: resolved
Blocked by: 05, 22, 23

## Question

敏感/不可逆操作的人工审核机制：危险工具清单的配置驱动模型（参照 DECO 的 yaml：name + required-state + hint + confirmation 多选项/带输入控件）；授权标记（state key）的会话级存储与放行语义（LLM 重调同工具时守卫识别已授权）；暂停/恢复工程形态——阻断后发确认事件给前端，用户选择经 REST 写回并发起续跑（依赖 22 调研：Spring AI 2.x 能否原生暂停/恢复，还是走 DECO 式「阻断 + state + 重试」）；确认交互的通道协议（SSE 自定义事件子类型？）；变更预览（COMMIT_PREVIEW 类富确认）的抽象边界——框架给通用 yes/no + 表单，业务级预览留给扩展？多实例部署下续跑请求打到另一台实例能否正确放行（state 必须持久化——依赖 06）？

## Answer

**定案：阻断+state+续跑重放 + 事件 schema 监听器透出 + 通用确认模型 + 一次性默认授权。**

1. **暂停/恢复**：守卫 beforeTool 返 BLOCK（带确认请求）→ 工具结果以「等待人工确认」文本回注模型结束本轮 → 确认事件经会话事件监听器透出 → 用户选择写回 SessionStateStore（06，跨实例可放行）→ 业务重发同一输入或调框架 resume API 重放最后一轮，守卫识别 state 标记放行。与 22 调研的最低成本路径（DECO 式）一致。
2. **通道协议**：框架只定义确认事件结构（confirmation 请求/响应 schema：多选项、带输入控件、hint），经 04 会话事件监听器透出；SSE/WS 由业务桥接，库不绑 Web 框架；事件同进可观测层。
3. **能力边界**：通用确认模型 = yes/no + 多选项 + 单文本输入控件 + hint 文案；变更预览通过 hint 嵌结构化摘要（如 diff 文本）实现，不建富控件体系；业务复杂预览走自定义前端 + 事件扩展字段。
4. **授权语义**：state key = 工具名 + 危险参数指纹哈希；默认同会话**一次性**放行；可配「会话内长效」（同类操作授权一次）；授权与撤销均记 Event。多实例：state 持久化（06），续跑打到任意实例均可正确放行。
5. **配置模型**：危险工具清单走 05 四层策略（name + required-state + hint + confirmation 选项/控件），通配匹配；19 的危险工具（write_file/run_command/http_request）默认挂守卫。

### 影响面

- 雾「HITL 确认交互的前端协议细节」依赖已消——确认事件 schema 在此定案，毕业清除。
- 雾「危险工具清单的行业默认模板」：25 的配置模型已定，剩「默认清单内容」细节，随 27（内置 Hook 清单）一并定。
